# هاست موردنیاز برای راه‌اندازی واقعی فمونا سنس

> 🔔 **تازه (۱۴۰۴):** پخش آنلاین وب (پلیر وب، ادامه تماشای وبی و تماشای گروهی) از پروژه حذف شد.
> تماشا و دریافت فقط از داخل خود تلگرام انجام می‌شود (`copy_message` از کانال Storage) که **هیچ ترافیکی روی سرور نمی‌گذارد**.
> نتیجه: پهنای باند دیگر دغدغه اصلی نیست و یک VPS کوچک برای هزاران کاربر کافی است.

این پروژه یک سامانه دانلود ویدئو با ربات تلگرام است. مصرف منابع عمدتاً توسط
**پردازش تبدیل کیفیت (FFmpeg)** و **حجم فایل‌های موقت (دیسک)** تعیین می‌شود — نه کد و نه ترافیک ویدئو.

## ۱) نوع هاست: VPS (سرور مجازی) — نه هاست اشتراکی

هاست اشتراکی (مثل هاست‌های cPanel داخل ایران) به هیچ عنوان مناسب نیست؛ دلیل:
- اجرای پروسه‌های دائمی (ربات polling، ورکر تبدیل ویدئو، ورکر runtime) ممنوع است.
- PostgreSQL و Redis و FFmpeg نصب نمی‌شوند.
- پورت‌های خروجی به api.telegram.org معمولاً محدود است.

**گزینه پیشنهادی (به ترتیب):**
1. **VPS خارج ایران** (آلمان/فنلاند/هلند) — دسترسی بدون فیلترینگ به api.telegram.org، پهنای باند بالا. تأخیر برای کاربر ایرانی ~۸۰–۱۵۰ms که برای تجربه‌ی چت/دانلود تلگرامی کاملاً قابل قبول است. پیشنهاد: Hetzner، Netcup، Contabo.
2. **VPS داخل ایران** — تأخیر عالی برای کاربر؛ اما خروجی به api.telegram.org ممکن است محدود شود (نیاز به پراکسی خروجی — بخش «پراکسی تلگرام» را ببینید). فقط اگر اپراتور سرور راه‌حل خروجی دارد.
3. ترکیبی: ربات+پنل روی هاست خارج؛ اگر ناچار به هاست داخل هستید، خروجی تلگرام را با `TELEGRAM_PROXY_URL` حل کنید.

## ۲) مشخصات سخت‌افزاری

### سطح شروع (تا ~۵۰۰ کاربر فعال)
| منبع | مقدار | توضیح |
|---|---|---|
| CPU | ۲–۴ هسته vCPU | ۲ هسته برای FFmpeg هنگام ساخت نسخه‌های ۴۸۰/۷۲۰/۱۰۸۰ + بقیه برای API/ربات/PostgreSQL |
| RAM | ۴–۸ GB | FFmpeg هنگام ترنسکد ۱۰۸۰p تا ~۲GB؛ بقیه برای PostgreSQL(۱GB)، Redis(۲۵۶MB)، uvicorn، ربات |
| دیسک | **۴۰–۸۰ GB NVMe کافی است** | ⚠️ ویدئوها در **کانال Storage تلگرام** ذخیره می‌شوند (رایگان) — دیسک سرور فقط برای فایل‌های موقت ترنسکد، خود سیستم و دیتابیس است. فقط اگر Bot API سرور محلی راه بیندازید، فایل‌ها یک کپی روی دیسک هم می‌گیرند (به حجم کتابخانه‌تان) |
| پهنای باند | ۵ TB/ماه کفایت می‌کند | بعد از حذف پخش وب، سرور فقط ترافیک API تلگرام و پنل ادمین را حمل می‌کند — بسیار سبک |
| سیستم‌عامل | Ubuntu 24.04 LTS | (پروژه روی ویندوز هم اجرا می‌شود ولی لینوکس پایدارتر و ارزان‌تر است) |

| منبع | مقدار |
|---|---|
| CPU | ۸ vCPU |

## ۳) الزامات نرم‌افزاری روی سرور

- **Python 3.13+** (پروژه با ۳.۱۴ تست شده)
- **PostgreSQL ۱۷** + **Redis ۸** (در مخزن `compose.yaml` آماده است: `docker compose up -d postgres redis`)
- **FFmpeg + FFprobe** (برای پردازش کیفیت — `FFMPEG_BIN`/`FFPROBE_BIN`)
- **Caddy** (قالب `deploy/Caddyfile.template` در مخزن هست): HTTPS خودکار با Let's Encrypt + پروکسی به `127.0.0.1:8000`
- **دامنه + SSL**: برای webhook تلگرام و پنل ادمین، https اجباری است (`PUBLIC_BASE_URL=https://…`). تماشا از خود تلگرام است و به دامنه/SSL وابسته نیست.
- اختیاری: **Docker** فقط برای Postgres/Redis؛ خود اپ نکسته اجرا می‌شود.

## ۴) ویدئوها کجا ذخیره می‌شوند؟ (معماری storage)

**ویدئوها روی هاست ذخیره نمی‌شوند**؛ مخزن اصلی، کانال Storage تلگرام است (هر فایل تا ۲GB، تقریباً نامحدود، رایگان) و سرور فقط «نقش واسط» را دارد.

**تماشا فقط داخل خود تلگرام انجام می‌شود:** ربات پیام کانال Storage را با `copy_message` برای کاربر کپی می‌کند — **هیچ بایت ویدئویی از سرور شما عبور نمی‌کند**. سه «حالت پخش» قدیمی (پلیر وب، لینک پخش خارجی/STREAM_URL به‌عنوان پخش‌کننده، پروکسی پخش از سرور) با حذف پخش وب از پروژه حذف شده‌اند؛ هیچ کلید env پخش‌وبی (و هیچ جدول حالت‌ها) دیگر وجود ندارد و نیازی به تنظیم آن‌ها نیست. تنها کلیدهای مرتبط با رسانه که باقی مانده‌اند، سمت دانلود/آپلود Bot API هستند (`TELEGRAM_BOT_API_BASE_URL` + `TELEGRAM_LOCAL_FILE_ROOT` — فقط برای Bot API سرور محلی، بخش ۵ را ببینید) و ربطی به نمایش به کاربر ندارند.

با این معماری:
- دیسک: ۴۰–۸۰GB فقط برای ترنسکد موقت + دیتابیس کفایت می‌کند
- پهنای باند سرور: فقط ترافیک API تلگرام + پنل ادمین (چند گیگابایت در ماه)
- هزینه‌ی «پخش» صفر است؛ تجربه‌ی تماشا همان پلیر داخلی تلگرام است

## ۵) نکات تلگرامی مهم (روی هاست)

1. **محدودیت ۲۰ مگابایت Bot API**: دانلود فایل با `getFile` برای ربات معمولی حداکثر ۲۰MB است؛ برداشتن این سقف فقط با **Bot API سرور محلی** ممکن است (`TELEGRAM_BOT_API_BASE_URL` به سرور `telegram-bot-api` خودتان + `TELEGRAM_LOCAL_FILE_ROOT` برای ریشه‌ی فایل‌ها) — این فقط مسیر دانلود/آپلود کارگر است، نه حالت پخش.
2. **ربات باید ادمین کانال Storage و کانال‌های عضویت اجباری باشد** تا `getChatMember` جواب دهد.
3. **webhook**: بعد از تنظیم دامنه، `python scripts/set_webhook.py` را اجرا کنید و `TELEGRAM_MODE=webhook` بگذارید.

## ۶) پراکسی تلگرام (TELEGRAM_PROXY_URL)

اگر سرور به `api.telegram.org` دسترسی ندارد (در لاگ Bot خطای `getaddrinfo failed` می‌بینید — مثلاً روی VPS داخل ایران)، همه‌ی ترافیک تلگرام (ربات، ورکر اعلان‌ها، ارسال رسانه) را از یک پراکسی عبور دهید:

```env
TELEGRAM_PROXY_URL=socks5://127.0.0.1:10808
# یا http:  TELEGRAM_PROXY_URL=http://127.0.0.1:10809
```

- طرح‌های مجاز: `socks5` / `socks5h` / `socks4` / `http` / `https`.
- کتابخانه‌ی `aiohttp-socks` از قبل در `requirements.txt` هست؛ وابستگی جدیدی لازم نیست.
- اگر خالی بماند، اتصال مستقیم استفاده می‌شود.
- اعتبار مقدار در استارتاپ سنجیده می‌شود: در production مقدار نامعتبر **fail-closed** است و فرایند بالا نمی‌آید (پراکسی خراب یعنی کل ترافیک تلگرام بی‌صدا می‌میرد — بهتر است همان اول دیده شود)؛ در dev فقط هشدار چاپ می‌شود.
- اگر می‌خواهید پنل و ورکرها بدون ربات بالا بیایند (مثلاً تا پراکسی راه بیفتد)، `START_BOT=0` بگذارید — رد شدن Bot عمداً غیرحیاتی (non-fatal) است و پنل/ورکرها آنلاین می‌مانند.

## ۷) چک‌لیست استقرار روی هاست

```bash
# ۱. زیرساخت
apt update && apt install -y python3.13 python3.13-venv postgresql redis-server ffmpeg caddy
# (یا docker compose up -d برای postgres+redis)

# ۲. کد و محیط مجازی
git clone <repo> /opt/femona && cd /opt/femona
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# ۳. پیکربندی
cp .env.example .env   # مقادیر production طبق docs/SYSTEM_STATUS_GUIDE_FA.md
python -m alembic upgrade head
python scripts/seed_initial_data.py   # فقط بار اول (ادمین ارشد و پلن‌ها)

# ۴. اجرا (سه پروسه جدا + ربات)
uvicorn app.api.main:app --host 127.0.0.1 --port 8000
python -m app.workers.media_worker
python -m app.workers.runtime_worker
python main.py            # در حالت polling؛ در webhook اجرا نکنید

# ۵. سلامت
curl http://127.0.0.1:8000/health/ready
```

هر ۴ پروسه را با systemd unit جدا (یا `register_tasks.ps1` روی ویندوز) بالا نگه دارید و لاگ‌ها را به فایل هدایت کنید.
